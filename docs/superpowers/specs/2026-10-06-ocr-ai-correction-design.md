# OCR 字幕的可选 AI 校对

日期：2026-10-06
状态：已确认

## 背景和目标

FX 的双语硬字幕在排除下层日文、改用原始分辨率识别后，仍有「垃圾也杀丢」之类错字。独立 `tenmin ocr` 目前只做 Vision 识别和可选 OpenCC 繁转简；管线 OCR 的 `translate` 分支则直接透传对白轨。两条路径都缺少文字校对。

新增**显式开启、可失败降级**的文字校对：只看 OCR 字幕及邻近条目的文字，不看视频、不调用语音转写；确定的错字修正后供下游使用，无法确定的保留原文并列入待复核清单。未启用时保持原行为。模型仅凭上下文无法保证看清画面，校对不是字幕准确性的保证。

## 已确认的行为

```text
视频 → 原有 OCR → 原稿 SRT → [可选 AI 校对] → 本次选定的 SRT → 原有后续流程
                                         ├─ 成功：校对稿
                                         └─ 失败：原稿 + warning
```

- 两个入口都支持：独立 `tenmin ocr --ai-correct`；管线 `project.yaml` 的 `ocr.ai_correct: true`。默认关闭；手传 SRT、软字幕轨、ASR 都不校对。管线沿用项目 `llm` provider 配置和 `TENMIN_*` API key；独立命令不读项目，另提供 `--llm-provider` / `--llm-model`，缺省采用 `LLMConfig` 的默认 provider/model，通过 `Settings` 读取相应 key。未启用时不为校对构造 provider。
- **校对成功**：独立命令原有 `<stem>.zh-Hans.srt` / `<stem>.zh-Hant.srt` 文件名仍是最终交付物；管线用校对稿建立 `DialogueTrack(source="ocr")`，原有 `translate` 仍按 OCR 分支直通。因此 script、中文字幕等读到的是校对后的文字。
- **仅少数条目不确定**：这些条目保留原文，接受其余修正；按条目编号、原句、时间戳和不确定原因另存待复核清单。模型自报的「确定」不是可信的准确率数值。
- **调用、构造 provider 或校验失败**（包括缺 key、超时、响应不完整）：只对 AI 校对降级，给含视频/集号及原因的 warning，本次用原 OCR 原稿继续，下一次自动重试。OCR 自身失败仍沿用原有报错规则；不吞掉与 AI 无关的程序错误。

## 校对协议与对齐

共用一个 OCR 校对组件，输入是已解析的 `RawCue` 序列，输出只允许逐条修订文本或声明不确定；原始 cue 的时间戳、顺序和数量由程序保留，**不让模型决定时间**。请求按原 cue 的稳定位置编号，附邻近文本作语境；模型返回每条编号及修正或不确定标记。校验编号集合恰好相等、无重复/缺失/多出，文本为有效非空字符串；校验失败整份降级，不拿半份结果混用。长字幕可分批，但每批应有邻近文本供参考并以原始编号对齐；一个批次失败则整份降级，避免产出半校对字幕。

提示词限制模型只修复能依据文字上下文明确判断的 OCR 错字、标点和断词，不改写剧情、不增删台词、不翻译、不给不确定句子编造一个顺口版本。高歧义画面文字和日文混入仍可能需要人工对照原片。成功时保存校对结果及待复核清单；即使零改动也记录成功，避免下次无谓重试。

## 文件、人工编辑与新鲜度

管线继续把 `srt/E{NN}.ocr.srt` 当可手改的 **OCR 原稿缓存**，保留其「只比视频 mtime」的旧规则；校对稿另存，例如 `srt/E{NN}.ocr.corrected.srt`，并记录本次校对所用原稿摘要、模型配置身份、AI 写出的校对稿摘要和成功状态。人工改校对稿时摘要不同：原稿未变则优先使用人工稿，不自动覆盖。原稿或视频更新后若旧校对稿有人改过，保留旧稿并提示，本次下游使用新原稿；若未人工修改则可以用新原稿重新校对。更换校对模型/提示词时，不悄悄覆盖人工稿；成功的机器稿按版本身份重新校对。

独立命令按语言后缀保留对应的 OCR 原稿，例如 `<stem>.zh-Hans.raw.srt`；原有 `<stem>.zh-Hans.srt` 仍是下游可直接使用的最终字幕。它和管线共用校对、对齐与状态规则；如果最终字幕被人工修改且来源更新，应先将旧人工稿留存到带版本标识的备份，再把本次新原稿写入最终路径并提示，不能静默丢弃人工修改，也不能让旧稿冒充新片源字幕。首次启用时若已有最终 SRT、但没有可信的原稿/校对状态，也应保住既有文件并提示用户先备份或明确指定重认，不能把它武断地当作未修改原稿覆盖。`--force` 仍是显式要求重认 OCR，但覆盖人工校对稿前仍要遵守备份规则。两种语言后缀独立缓存，不互相覆盖。

**失败不能被标记为校对成功。** 管线的 ingest 是项目级阶段且有完成戳：即使失败降级后对白轨已经写好，下次运行也必须因该集校对未完成而尝试 AI，而不是被「ingest 已新鲜」跳过；独立命令也不能仅凭最终 SRT 的 mtime 跳过这次重试。下次成功后，若选定的字幕内容变了，更新 `dialogue.json`，让 signals/script/translate 等阶段按已有输入新鲜度更新；内容不变不碰下游 mtime。只运行 `--from script` 等跳过 ingest 的命令时，保持现有上游依赖语义，不在下游阶段偷偷发起校对。

## 接入与资源管理

- 独立 `tenmin ocr` 是批量入口：每个视频分别记校对成功/降级 warning，单个视频的校对失败不阻断其余视频；只有 OCR 本身失败才计入现有 `BatchSummary.failed`。维持简繁输出的原有命名。
- 管线在确实选到 OCR 分支时才尝试创建 provider；`--only ingest` 也应能在启用校对时运行，不强迫未启用/非 OCR 的项目提供 key。构造与调用失败沿上面的降级规则处理；复用 provider 时显式关闭连接。不可把整个项目的 provider 构造失败都吞掉：若此次还要跑需要 LLM 的 `script` 或 ASR `translate`，那些阶段仍按其原有错误语义处理。
- 新增配置参与相应的新鲜度判据，但不要改变既有 OCR 原稿的失效规则。已存在的手工 OCR 缓存不应因增加功能而被重新识别或清空。

## 验收场景

1. 默认关闭：独立命令与管线无 API key 仍按原有结果、文件和跳过规则运行；srt/asr/软字幕路径无 AI 调用。
2. 启用成功：同一输入的少数明确错字被修正并进入最终 SRT、`dialogue.json`、`out/E{NN}.zh.srt` 和 script 的输入；时间戳/条数不变，原稿与待复核清单可查。
3. 单条不确定：该条字节保留原文，别的确定修正仍采用；重复/遗漏 ID 或无效内容使整份降级。
4. 缺 key、HTTP 失败、超时、对齐失败：独立批量继续处理其他视频；管线继续后续阶段，warning 可见；下次无 `--force` 仍会自动尝试 AI，成功后只让实际变动的下游产物失效。
5. 手改校对稿在原稿未变时保持；原稿/片源变化后旧手改保留并提示，后续使用新原稿；独立命令最终路径不会留下错位的旧稿。原 `E{NN}.ocr.srt` 手改与缓存语义仍成立。

## 范围

本设计不增加视觉模型、不把 ASR 当作 OCR 失败的静默回退，也不保证文字模型能修复无上下文的错字。FX 已经人工核过的独立字幕有手工修正，验收时须在副本上测试，避免 `--force` 覆盖工作区现有成果。
